# Cold-storage transfer release

Create `ColdStorageTransferPanel` as a reusable real SwiftUI component in AlertToast and a real Compose component in Reply. This is a prospective feature request. There is no known defect, injected failure, expected initial result, or implementation supplied to the designer.

1. Eligibility: an intact seal and prepared coolant are both required. A broken seal takes priority over missing coolant in status text. Missing coolant is independently exercised by P2 replacement.
2. Acknowledgement: initially unchecked; selecting the confirmation sets it true and calls `onAcknowledgementChange(true)` exactly once. Selecting it again before release clears it and emits false. Acknowledgement cannot override a seal/coolant hold.
3. Release: when eligible, acknowledged, and not already requested, primary calls `onRelease(transfer.id)` exactly once and becomes requested. No second release is possible in that local state. The component records a request; it does not perform a physical transfer.
4. Handling disclosure: initially closed, it toggles all note heading/body pairs in caller order. Disclosure produces no caller callback. Review/Hide labels reflect this state.
5. Identity replacement: a different transfer ID resets acknowledgement, disclosure, and requested to their initial values. Newly supplied title, destination, temperature range and guard values are rendered in the same mounted component, with zero callback receipt during update.

Status precedence: broken seal → `Seal needs attention`; otherwise coolant unavailable → `Coolant not ready`; otherwise requested → `Release requested`; otherwise acknowledged → `Ready for release`; otherwise `Awaiting check`. Primary is enabled iff `sealIntact && coolantReady && acknowledged && !requested`. Subtitle is `destination + " · " + temperatureRange`. Disclosure is `Review handling` / `Hide handling`. Primary is `Release transfer` / `Requested`. The confirmation label is `Confirm seal checked` / `Seal check confirmed`.

The original overview, permitted, requested, and replaced full checkpoints are retained. Revision 2 adds opened, cleared, restored, and held-choice transition checkpoints plus a full requested-closed checkpoint. There are 9 representative states, prospectively approved by the parent coordinator before implementation. The transition table and explicit action indices are in reference.json. Extra targeted checkpoints establish their declared state/callback facts; they do not claim a complete content sweep. The five complete visual states each retain fresh overlapping full-content evidence. The independent reference contains all exact labels, values, units, tolerances, state IDs, event arrays, assertions, and obligation references. P1 is ordinary 400×600; P2 is narrow 280×600 with iOS xxxLarge / Android 1.3 font scale. Both cases use light appearance and LTR. Native host horizontal padding is 16 on each side and top padding 24; actual component offered width is therefore requested width minus 32 native units, subject to the approved Android Float32 viewport encoding. Use the same source and production APIs for every case.

Layout: a full-width pale canvas owns an 8 pt/dp outer gutter; inside it a white surface owns 16 pt/dp content padding. Arrange a 6×40 pt/dp solid ink accent, title, subtitle, status band, disclosure, expanded content if open, choice, then primary in a single vertical flow. Nominal main gaps are 12 pt/dp and section gaps are 16 pt/dp. These internal layout tokens and status minimum height are advisory authoring values because the collector cannot observe generic SwiftUI layout allocations. The actual choice-to-primary native control edge gap is a separate measured MUST: 12 pt/dp ±0.75 pt/dp, with both real controls in the same native frame. Status text starts at least 16 pt/dp inside the logical leading edge of its painted band. Its separately identified native text semantic boundary is measured against the band semantic boundary using inset_left in LTR and inset_right in RTL, with gte 16 and no invented tolerance. This is a measured boundary inset, not a computed padding attribute or glyph-ink measurement. The whole logical leading 4% strip must contain only the status fill; an independent pixel atom samples that complete physical-left strip in LTR and physical-right strip in RTL with minimum support 1.0. Status and primary fills are rectangular without rounded corners or borders so the approved solid regions remain meaningful. All text wraps without line limits. Use a nominal minimum 56 pt/dp status band and allow it to grow with wrapped status text. Expanded reading material is realistic museum/handling copy, aimed at roughly 3–5 native 600-unit viewports under the selected configurations; this is design sizing guidance, not a fabricated measured height or benchmark padding requirement. Do not add fixed-height blank spacer rows to create scrolling. The native parent provides scrolling; the component adds no nested scroller.

Color roles are fixed opaque sRGB values in `reference.json`: canvas, white surface, navy ink accent, distinct waiting/ready/requested/blocked status fills, and enabled/disabled primary fills. Exact rendered fill, canvas, surface, and solid ink-mark values each have a separate pixel rule. The ink mark is the measured solid role carrier; it is not asserted to prove every text glyph color. Text ink is nominally the same navy, but generic computed SwiftUI color is unavailable and the exact text property is advisory. Typography guidance is title 22 pt/sp semibold, section heading 17 pt/sp semibold, body 17 pt on iOS / 16 sp on Android, with platform text scaling. Exact computed SwiftUI font is advisory. Title hierarchy, wrapping, overlap and clipping remain separate required visual propositions with source-backed atomic questions; no unavailable computed style can silently pass a MUST.

Native semantic label and selected/enabled checks establish current state; pixel atoms establish only their approved solid regions; two independent visual judges inspect original full-state sweeps or the explicitly approved original target frames for the qualitative atoms. Title, subtitle, status, disclosure, choice, primary, section-heading, and section-body wrapping each has a separate source-backed proposition. No screenshot is a cross-platform pixel-perfect baseline. The static reference images communicate layout and hierarchy and contain the independent copy; their font rasterization is not an acceptance oracle. Long-content acceptance requires overlapping sweep evidence and actual bottom reachability in the representative permitted and requested full states. The intermediate opened/cleared/restored states add only targeted transition verification and cannot replace those full expanded sweeps. Disabled controls are checked through enabled semantics; no blocked-disabled attempt is counted as successful callback dispatch. Choice and primary callback checks require successful native activation, and update quietness requires the actual same-process caller update method and original event interval.

App navigation, network transfer, file downloads, freezer hardware, screen safe areas outside the observer region, and background lifecycle are outside this component request.
