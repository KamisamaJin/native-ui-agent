# v9：需求路由、统一执行与定向复验

本轮把需求与发现的处理、统一执行计划、源码绑定的复验规划做成可执行工具，再验证同代码同覆盖的采集速度，最后用两项全新需求的同一份初始 PR 进行 v8/v9 增量对照。原始数据与失败保留；离线 CI 验证来源、封存与复算，不重新运行 SDK，也不表示组件验收通过。

## 结果：采集提速成立，质量优势没有成立

共享 iOS 采集在四组同源码、同要求覆盖的配对中降低约 **61.31%** 耗时。新的决策工具没有在这次盲测中带来整体质量优势：两组都没有确认的产品缺陷分母，最终均未通过完整验收；新版保留了更多可定位性相关未知项。到完整自验结果的可归属路径均值 **33.60 → 31.88 分钟**，约少 5.1%，但这是到失败验收结果的耗时，不能解释为更便宜的成功 PR。

没有确认分母不是“没有真实缺陷”的证明，也不能写成零漏检或 100% 修复。十个原始严格标签 F 来自同一组装饰文本/语义采集现象；评审没有足够证据把它确认为真实平台可访问名称或业务错误。两组后来都让这些原始断言通过，但仍属于**测量表现恢复，产品责任未裁定**。十条告警全部保持 U，条件误报占比不可计算；保守告警误报范围仍可从 0 到 100%，经典 FPR 不可得。

全部 44 次业务采集请求保留，其中 11 次为不完整采集回执；这不是 11 个独立产品 bug。源码、执行范围、覆盖、原始图片和评审均可追溯。两轮独立判断、原始告警判断和派生指标在正式揭盲前关闭；零分母、失败及未知没有通过换任务、注入缺陷或放宽标准补齐。

## 新工具的收益与仍然存在的瓶颈

**同覆盖后端提速可确认，agent 决策收益只能作局部观察。** T1 两组均未修改组件，最终各有 9 个 Android P2 必需像素未知项。T2 新版用一次反馈、约 462 秒编辑处理 Android 装饰叶节点；旧版用两次反馈、约 635 秒编辑，并继续处理 iOS 容器的真实 AX 分配。旧版最终把 iOS 表面标记及相关测量恢复为可评估，新版留在未知：公开多 10 U，加上隐藏场景共多 15 U。不能把少一次反馈而未关闭必需观测直接说成效率优势。

T2 新版确实执行了四次需求路由 CLI；但两次候选运行均没有记录 `retest_plan.py` 的实际调用，复验状态由 agent 自行选择。规划器有可执行实现、源码与原图篡改控制及中性验证，**这次真实开发没有证明它自动接管了复验选择**。一次对两次请求的差异不能直接归功于规划器。相关原始记录见 [新版路由执行](participant-completion/u-695819ff/original-routes/)、[新版修复记录](participant-completion/u-695819ff/repair.json)、[旧版修复记录](participant-completion/u-5184cc6d/repair.json)。

因此当前瓶颈不是少几个观测项：已有必需 U 尚未稳定转化为可执行的定位诊断和闭合任务，工具可用也不等于被调用。与此同时，合成的未合并语义标签不能直接充当真实平台标签的产品判据；遇到这类分歧应先验证测量语义。最终必需像素采样也仍存在可评估性缺口。源码审查和最低 API 校验通过，并没有消除这些缺口。

下一轮应让执行服务默认消费经过来源校验的发现与复验计划，为未关闭的 MUST 明确执行诊断或给出不可验证的证据；测量判据的语义要先在无关探针上确认。当前冻结版本及本轮任务没有据此改写或重跑，避免针对已知现象调优后重算。

设计与协议准备本身也很贵：共享准备墙钟 **118.15 分钟**；中性工程与冻结 **91.11 分钟**；外部独立评分和告警判断 **70.32 分钟**。自预注册至揭盲的研究墙钟 **351.46 分钟**，发布与 CI 另计。它们包含并行工作及操作员等待，不能当作单 PR 活跃工时；也不能从生产成本讨论中隐去。完整逐项时序在 [TABLES.md](TABLES.md) 和 [summary.json](summary.json)。

## 可执行改动

`requirement_routes.py` 从独立批准的需求索引生成状态与断言对应关系，把缺少契约路径、环境错误、证据缺失、判据分歧、源码诊断和观测能力问题分别交给后续行动。必需项不能因没有可用测量而变成通过。定向范围内没有请求的状态延期到完整验收，保留原有 U。

`execution_plan.py` 从同一份独立计划生成动作、动作后观测和覆盖范围，绑定原始桥接、调用数据、源码前后指纹与图片哈希。iOS 合并同一新鲜状态扫描内的目标观测，保留真实派发、即时帧、状态版本与完整滚动要求。

`retest_plan.py` 把原始失败、实际源码改动和批准的回归依赖转换成复验状态；实测模式拒绝未修改的源码、被替换的报告、图片或源码根目录。它提供规划能力，不能证明未检查状态安全，也不替代新源码的完整最终验收。

核心在新业务设计前完成中性原生验证并冻结，132 项工具测试通过。独立反馈指出的范围误路由和视觉失败来源绑定问题已在冻结前通用修正；没有针对新业务的控件名称、文案、配色或字体写分支。详见 [工程记录](ENGINEERING.md)、[决策协议](../../native-ui-agent/references/decision-feedback.md)。

独立固定中性组件、调用数据与覆盖要求，普通宽度和窄屏大字各做两次配对，第二次交换旧/合并策略顺序。四组均保留要求的状态、目标和成功派发回调；每次自动结果均为 54 P、0 F、12 U，没有已知支持项丢失或结果冲突。独立看图同时保留两种策略共有的自然禁用配色问题，没有修正该组件以制造成功。

## 盲测设计与共用基础设施

独立上下文设计 Cold Storage Transfer Panel 与 Offline Audio Tour Panel，固定 API、参考图、带单位的值、动作、逐状态规则和源码审查索引，再经过独立可行性审查。两个未获通过的静态设计提案原样归档，均发生在生产源码及业务渲染之前。最终设计分别有 9/10 个状态；公开场景为普通宽度、窄屏大字，保留场景加入新调用数据与 RTL。

每项需求只有一份自然编写的 SwiftUI + Compose 初始 PR。编写阶段只允许编译；两项初始源码全部封存后才采集 D0。两修复条件收到字节相同的该项初始源码及 D0 证据；没有人为注入缺陷，也没有看到缺陷人口后替换任务。每组最多 20 分钟编辑/诊断，包含等待，最多两次内循环原生请求。源码封存后立即运行自己的完整公开验收，再看原始新图、完成源码审查与实际最低 iOS 源码/API 校验；不再允许修改代码。

两组均使用 Skill，对照为 v8，实验为 v9。它们共享优化后的执行后端、真实环境检查、源码/图片绑定、最终 MUST 门控和评估器。因此盲测比较的是额外的 agent 决策工作流，不能把共同的后端或门控收益算成 v9 独占收益。

全部四组完整自验端点关闭后才启动隐藏场景；随后初始与最终阶段各由两个新上下文独立评审，同阶段全员封存后才能进入下一阶段。原始发现和根因分组另做两轮独立判断，最后才正式揭盲。最终公开独立评分使用各组自己最终采集的同一份原始字节，没有另外重渲染代替。

共享基础设施的两个成本问题单列保留：D0 的冻结配置为两项任务选择了同一 iOS 槽位，产生实际排队；源码审查使用上游相对路径，而组合工作区带有项目目录前缀。后者通过显式内部目录视图恢复，生产哈希、预期、冻结工具和既有审查目录均未改变，原始失败和恢复耗时保留。它不是产品修复或新版工具收益。详见 [工程记录](ENGINEERING.md)、[路径恢复证明](operators/source-view-compatibility/)、[排程记录](operators/initial-acquisition-scheduling.json)。

## 解释边界

原子失败行可能重复同一根因，源码违约与运行时表现分开报告，不相加当作独立 bug。严格断言 F 不等于产品缺陷；无足够证据的责任归属、原始告警和评审分歧保持未知。零分母为 N/A，U 不算修复或通过；经典 FPR 缺少完整 TN 分母。

两项受控组件任务不是广泛 native PR 人口。iOS 使用 Simulator/XCUITest，Android 使用 Paparazzi/Compose JVM 语义动作；不证明物理触摸、原应用完整页面/导航/后端，或通用 SwiftUI 计算样式树。最低 iOS 校验仅证明实际模块与调用方的源码 API 可用性，未证明旧系统打包、链接或运行。独立双 AI 一致不是人类金标准。

成本分别保留从接手到自动结果、到完整自身验收端点、初始编写与初始采集、实际完整墙钟、设备排队与可重叠的资源时间，以及共同设计/协议准备、研发和外部评审阶段。失败端点仍计成本；没有成功验收就不能声称成功 PR 交付成本更低。tokens 和金额没有精确记录，保持未知。

完整结果与失败记录由固定脚本在正式揭盲后生成：[指标与成本](TABLES.md)、[统计原值](summary.json)、[原始界面](GALLERY.md)、[失败与未知索引](failure-index.json)、[复算](REPRODUCE.md)。
