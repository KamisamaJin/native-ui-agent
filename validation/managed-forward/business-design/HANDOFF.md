# Fresh Menu Change design handoff

The public and private scopes are complete, independently authored before any component implementation, and separately sealed. Give only `public/README.md`, `public/API.md`, the public structural SVG and public inputs to the natural implementation author after independent approval. Keep the private scope and this root handoff outside that author's context.

Both scopes request the same two production files and fixed API. Public case: `cedar-lunch`. Private case: `evening-service`, one combined narrow / large-font / dark / RTL configuration with different order, option IDs, text, prices, limits and revision reconciliation. Each scope has eight selected business states on one continuous action path. The public update keeps a valid option and clamps quantity; the private update invalidates the selected option and withdraws credit. These are ordinary published product rules, not planted defects.

Each platform plan has 39 rules × 8 states = 312 dispositioned cells and 303 applicable assertions. There are seven independent manual-rule policies (three rendered-region color atoms and four qualitative image atoms), 17 required source claims and 39 corresponding native/image responsibility claims. These are design counts, not empirical checks passed or a defect denominator.

The input design was mechanically sealed and compiled with frozen candidate-v12.6 `design_contract`, `review_contract`, `requirement_routes` and `execution_plan` APIs. Baseline-v11 also reconstructed the four existing generated plans, policy catalogs and route audits without changing expectations. Both checks reported empty mandatory route gaps and empty unowned assertion lists. `python3 prepare.py --verify` recomputes the exact design bytes without changing them. Normal `prepare.py` requires fresh generated output paths and never modifies an input expectation. No SDK, simulator, Paparazzi render, native source review or image judgment was run.

`approval.json` in each scope intentionally says `awaiting_independent_design_review`. It is a preparation summary, not an author-issued approval. The root owner must retain a separate original independent review citing these two scope seals before implementation. Design changes require a new seal and retained review; do not change expected values after seeing implementation output.

Integration conventions match the root owner: `integration.json` lists only workspace-relative single-file production paths and `responsibility_ref`; `approval.json` lists `design_lock_sha256`, `policy_sha256`, `routes_sha256`, `environment_sha256[case][platform]`, and `launch_ref[case][platform]`. Launch records are in `/launch/<case>/<platform>` of the independently locked reference and pin the fixture canonical digest plus actual bridge file-byte digest. The two scope bridges are byte-identical and contain only decoding and a direct production call.

The independent reviewer should resolve any semantic ambiguity before approval, particularly the business reconciliation rules and whether the chosen native semantic/control boxes support the declared gutter samples. The sample rectangles were chosen from guaranteed source padding, but no native run has yet established their observability. Unavailable semantic mapping or insufficient support remains unknown, never a guessed pass or automatically attributed product failure. If a sample definition is judged inappropriate now, revise the preimplementation design and reseal it before source creation.

Mandatory source duties have independent links through `reference.source_obligation_routes` and each associated `routes.reason`. The preparer verifies only the completeness of these associations. The frozen route auditor does not execute source routing; source claims remain separately mandatory through the default responsibility gate with actual component/bridge file subjects. Source font/padding/palette intent is not represented as an AX computed style. Runtime rendered regions and qualitative wrapping/hierarchy/clipping/overlap are distinct atoms. Geometry explicitly measures the actual send accessibility/control box, not layout padding or physical touch.

No further external information is required to implement the published product. Remaining actions are independent design approval, natural source implementation from public inputs, then source-bound native collection and independent acceptance. No product fault is guaranteed or required for this design to be valid.
