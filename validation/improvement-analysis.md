# 首轮无增益的证据分析与改进边界

依据 a570af1 的冻结源码、D0/FINAL 盲评和检出匹配。下述改进先于新任务实现，原始试验与 Skill v1 完整保留，不重写旧得分。

## 可以从首轮得出的结论

| 证据 | 解释及边界 | 对应改进 |
| --- | --- | --- |
| 两组均获详细独立需求、参考和已接好的原生宿主；业务派生逻辑均未确认失败 | 强对照已共享 Skill 的大部分前置价值；只测到了剩余流程/runner 的增量。不是“Skill 普遍无用”的证据 | 新试验同时比较无 Skill、冻结 v1、改进 v2；统一宿主与时间预算，不把任务变化归因于新版 |
| 两组均观察到窄屏重排；严格 rule_id 匹配 TP2/FN1，三失败项仅一缺陷簇 | 33.3% 不等于漏了三个独立问题之一，包含规则归因遗漏；需要同时看根因检出、明确规则命中和独立问题 | 增加需求×场景×方面的证据账本；发现问题后检查关联规则，不自动复制失败/检出信用 |
| 首轮 Skill 提醒“看完整图”，但未强制形成底部采样证明；最终每组145项未完整评估 | 文字要求没有转成可执行的覆盖检查。更多截图并不自动等于更多覆盖 | 增加有证据指纹的覆盖汇总；缺项不能通过；滚动需实际底部/目标可见证据和重叠截图 |
| 单测 UIHostingController 的 AX 为空，iOS交互只能读源码 | SnapshotTesting 的渲染路径无法替代实际 App 的辅助功能与交互路径 | 增加独立 App+XCUITest 观测适配器，能力探针先验证实际 AX、点击回调、同进程调用方更新与滚动 |
| 暗主题未同步系统外观，引出两组共同的配色误报 | 宿主契约未经验证，会污染产品评价 | 通用探针检查系统外观、实际宽度/字体类别/方向、目标测试数及事件追踪；能力失败与产品缺陷分列 |
| 新旧 SwiftUI 宽度观察/修复路径不同，最低系统只作类型检查 | 最新模拟器通过不能证明最低 OS 的视觉正确；小 diff 也不是自动质量分 | 记录运行时矩阵及回退路径，不把声明可用性当作运行时覆盖；本轮不承诺提供通用SwiftUI样式树 |
| 一个需求、两个相关平台、一次运行、共享缓存 | 无法分辨随机性、资源争用和稳定收益 | 新需求由新上下文独立设计；三臂同题比较；时间仅作描述，零缺陷分母记N/A，接受新版无优势/更差的结果 |

## 本轮不做的推断

不会把旧参考或旧失败条件硬编码进 Skill，也不以指定宽度、控件名或 RTL 个案定义普遍成功。v1 使用旧哈希快照；v2 的新增能力面向通用证据覆盖与运行时观测。新设计者不读取这里、旧报告或 Skill；全部新需求与验收在实现前冻结。

新实验具体输入保持私有至评分封存；公开规则一致。共同宿主/工具可供三臂使用，v2额外流程和覆盖工具属于待检验干预。旧用例只验证回归与能力接入，不计入新需求效果分母。任何因新实验结果而产生的后续改动必须另起版本，不能回填本轮评分。
