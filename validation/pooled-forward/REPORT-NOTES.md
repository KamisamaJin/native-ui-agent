## 可以确认的结果

同代码、同覆盖的 AB/BA 资格验证通过预先规定的门槛：采集墙钟从 910.361094 秒降至 680.097815 秒，减少 25.293620%。14 组各104项原生判定一致，必需未评估项没有增加，8次最终平台资源收尾通过。该结果限于单机、热共享 SDK 缓存和独立授权的有限组件工作负载。设备复用、完整截图包采用和源码/平台证据失效是不同机制，不能相互冒领收益。

五个新业务任务均先完成独立设计与验收封存，再生成自然初版、仅编译、按字节复制给两组。五个初版全部固定后才启动业务界面。十组最终源码、自验和资源记录封存后才开启隐藏验收；独立匿名双评、共因匹配和实际观测共识封存后才揭盲。没有为扩大缺陷分母而修改生产代码注入故障。每项使用同一份初版、两组各20分钟源码窗口和最多两次诊断，早封不可解锁。

对照为 v12.6 加已列出的18路径共同正确性修复；新版为冻结 v13.9。这里没有测量“完全不用 Skill”的开发者。共同修复、控制器恢复、外部资源监督、独立评审和出版工具均不能计入新版独有收益。

揭盲后的原始源码核验确认：五项任务中，两组最终各85个生产源码成员全部逐字节一致。因此这批样本没有显示新版产生了额外的代码修复。可直接审查 [最终十个组件源码](production-examples/README.md)；它们是原文件的逐字节副本，没有作为新测试输入或评审证据。

独立评审确认的候选人处置组件问题是 **iOS 禁用原生 Button 后，角色填充色被系统状态渲染改变**，不是点击命中范围错误。两组都报告并修复了同一个问题。两组其他最终生产源码也一致；不能因为断言更多，就声称修复了更多真实业务问题。

## 必须单独披露的协议冲突

原始共因匹配保留五个“未满足文档安装目录”的项目：五份 API 文档要求 `Sources/AlertToast/Business/<组件>.swift`，给定执行配置及来源审批却绑定 `Sources/AlertToast/<组件>.swift`。后续独立、只读的 [执行范围审计](publication-initial-scope-audit-v1/REPORT.md) 证明了这个不一致。

修复规则仅允许修改原两个新增组件文件，并冻结其他输入；普通同策略源码版本审批不能修改安装路径。因此在提供的配置与普通修复流程内，不能同时满足这两项要求。作者笔记并不能代替原始调度或例外授权；本审计也没有证明全部历史调度的具体文本、物理上绝不能迁移文件，或任何人为故意注入。

原始封存判断和固定统计器中的这五项全部保留，不事后删掉以提高通过率。它们必须与真正的视觉、业务缺陷分别解释：不能用这些目录项证明某组 native 质量较差，也不能把原规则下的零完整交付简单解读成五个真实产品均不可用。新的审计是单独封存的附录，没有修改原 matcher 的任何成员。

## 成本与误报的含义

业务批次没有预先批准完整截图包的有效复用窗口；运行后没有补授权。两组完整包采用次数均为0。两组各有11次 iOS 新采集；Android 新采集为对照11次、新版10次。新版三次设备入池后都在约300秒到期被清理，下一次需要设备时已超过有效期，所以没有设备出池复用。不能把资格验证的25.29%直接套用到这批 PR。

原公开 PR 墙钟包含 D0 入队到各自封存的排队、源码与看图审查、SDK 生命周期、修复、复验和收尾。五次尝试均进入总耗时，失败没有排除。外部监督还会反复扫描整个研究目录；这个开销在原始时钟中真实存在，不能扣掉来宣称提速。其单机、研究环境特征也限制了对普通生产 CI 成本的外推。

封存后的原生隐藏验收、110步实际观测绑定、共享初始参照、匿名双评、匹配及准备成本分别列出。初始代码作者、全量设计和共同设施成本没有完整可审计测量时保留未知，模型 token/费用也保留未知。部分阶段时长不能冒充完整研究总成本。零完整交付时，“每成功 PR 成本”为 N/A，不是0，也不以只完成部分证据的尝试代替成功样本。

隐藏原生部分使用审计选定且不重叠的已测执行段；封存后机械绑定使用每个原调用完整外层墙钟，包括保留的失败。二者之和是已测成本，不是涵盖全部准备、屏障等待和未测间隙的完整评估 gross 墙钟。原段清单、选择依据及未解决的时钟差异保留在 `AUDITED-COST-BASES-v1.json`，未知部分不补为0。

误报采用 FDF：独立否定的缺陷告警除以已裁定缺陷告警。没有真阴性分母，不能称经典 FPR。错误的正向验证声明、未裁定的声明、缺失观测、基础设施失败与产品缺陷告警分别统计。封存后的独立发现不算开发循环已检出或已修复。

必需未评估比例使用初版前冻结的8232个适用义务/组；另外2100个预先不适用项/组不算通过。无效来源引用、缺少当前状态/截图绑定、没有能力测量的项目都保留 U，不能把一部分已观测子集重新定义成完整覆盖。

## 可外推范围

iOS 使用 Simulator/XCUITest；AX 不是通用 computed-style 树，精确几何由有界校准支持。Android 使用 Paparazzi/Layoutlib 与 Compose 语义动作，运行于新的 JVM，不等价于 Android 模拟器的 OS 触摸。受控新组件中使用最小定位标记。此批次没有证明任意旧工程零修改、完整应用导航、真实 BE 集成或发布就绪。

这五个复杂需求属于相关的业务流家族，且共享单机工具链及模型背景；不能把五对结果当作五个完全独立、足以估计普遍胜率的样本。源码一致能证明没有新增代码修复收益，不能代替独立的像素或行为判定。

磁盘是原始规定窗口内的采样分配字节峰值；目录扫描不是原子操作，实际采样间隔也长于名义2秒。不同 PR 的峰值不能相加当作同时峰值，也不能称精确瞬时或 APFS 物理占用。归档/只读重放的额外峰值与 PR 运行窗口分别列出。

全部原始失败、初版/最终源码、PNG、原生事实、xcresult、SDK日志、来源引用、判断分歧、时钟和磁盘记录按预定策略封存；精确传输核验与只读原键重放后才清理归属已确认的生成文件。清理不涉及共享 SDK/JDK/Gradle、用户模拟器、上游或主仓库 Git 数据。

## 从本轮证据得到的下一步

优先消除契约与执行配置之间的冲突，并在初版前验证“要求能否在授权修改范围内实现”。然后减少默认链路反复扫描和重建相同来源证明的成本，将资源检查限制在确定的失效边界内，仍需保留源码、环境和新设备事件的可靠失效。最后再用来源范围一致、不同 UI 家族且复用权限事前明确的新样本，测量修复产出和完整交付成本。这些是后续实验建议，本轮冻结工具、规则、过期时间和判定阈值没有为已知用例改动。
