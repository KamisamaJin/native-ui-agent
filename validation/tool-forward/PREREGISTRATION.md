# Tool-capability forward test (prospective protocol)

This protocol is fixed before any new business implementation. Generic tools are
engineered without reading the independent new business design. Their native probes
use unrelated controls, state changes and tall content, with expectations frozen
before candidate output. Old Skill/tool bundles and all unsuccessful native attempts
remain available; the prior experiment's scores are not rewritten.

## Independent design and resource control

The independent designer receives no tool implementation, old failures or outcomes.
The original design commitment is retained. Its size-only revision, if selected,
is requested prospectively from counts alone before any implementation: 6 initial
cases,2 unseen holdouts, at most3 full visual checkpoints/case and2 caller updates.
This reduces redundant native work; it does not select requirements from results.
The selected design and all mandatory atomic/group member IDs are committed before
implementers see any task. Group passes require ALL mandatory members; missing
members remain unassessed, never averaged away.

## Two arms and common boundaries

Compare the previous released tool capability with candidate v3, using the same
model/reasoning settings, public design, pinned Reply/AlertToast commits, machine and
budgets. Exact model service build/random seeds/token cost are unavailable. Each arm
has fresh context and a clean pinned checkout; no old business component is copied.
The baseline Android interface is a factory-only adaptation of the previous sampler;
its original sampling/action policy is retained and its diff disclosed. It is not
claimed that an Android generic CLI was already shipped in the prior release.

Both arms get the same action/bridge contract and review task. They receive only
their assigned capability bundle. Core task prompts do not teach a suspected defect
or provide grader findings. Instructions necessarily route to each bundle's actual
commands, so the development comparison includes tool discovery/instructions; a
paired collector comparison below isolates capture differences on identical code.

- D0: max25 active wall minutes total across both platforms. Compilation and one
  public example integration allowed; no product-image self-review before sealing.
- Read-only review: max12 active wall minutes after D0 grading seals; only own
  initial inputs/evidence and assigned tools. Findings identify exact case/state/
  aspect, certainty and sources. No source changes.
- Repair: one max15 active wall-minute iteration using only own sealed review and
  public design. No independent grader feedback, another arm or unseen holdouts.
- Final: seal both final sources/reports before revealing hidden concrete inputs;
  independently rerun all8 cases. Preserve any overrun/late evidence explicitly.

## Measurement and paired collector ablation

For independent D0 and FINAL ground truth, use the same candidate observation host
on BOTH anonymous source archives. Thus native assessment capability is equal for
quality grading, while the old arm's D0 self-review receives only old-tool evidence.
Its same D0 implementation additionally runs the old collector on identical inputs.
Compare actual input/state coverage and action evidence in this paired capture;
absence of a new JSON field alone is not a failure of old evidence. The evaluator
may credit supported original pixels, callbacks and overlapping views independently.
Do not reuse candidate-only evidence as if the old reviewer had seen it.

Adapters call actual production components. iOS: real app/XCUITest/native hierarchy,
actual taps/callbacks and same-process input replacement. Android: one attached
ComposeView/Paparazzi, native semantic actions, touch bounds/text layout and native
ScrollState; no physical OS touch/Activity claim. Source/API minimum deployment
checks are separate from legacy-OS runtime claims. Unavailable SwiftUI font/padding/
physical-hit-region properties are explicitly unassessed when required.

## Outcomes and blindness

Independent grading sees anonymous production and raw evidence, NOT Skills, arm map,
self-reviews, repair summaries or prior conclusions. All D0 grades seal before
self-reviews; all final grades seal before self-review matching; matching seals before
unblinding. Different evidence formats can reveal capture capabilities, so this is
procedural assignment blindness on a shared filesystem, not adversarial OS isolation.
The root operator knows assignment, performs no outcome grading and fixes no business
source. Common infrastructure corrections require retained attempts, a generic probe
and uniform affected reruns; they are engineering costs, not product fixes.

Report required atomic assessment counts and per-state pass/fail/unassessed, including
individual members of parameterized assertions; no half-rule full pass. Confirmed
D0 defect clusters and case/state/aspect failures are separate. Exact TP/FN requires
matching actual supported condition; related assertions earn no automatic credit.
FP requires a confirmed claim contradicted by adequate same-aspect evidence; suspected
issues/unavailable evidence stay uncertain. Miss rate FN/(TP+FN), N/A for zero defects.
Repair success resolved confirmed D0 failures/confirmed D0 failures; report regressions,
previously unassessed/newly observed defects and held-out evidence separately. An
unexecuted action's zero callbacks is not a product failure or pass.

Retain active phase times, operator/native/queue costs and independent judgement
limits. Native capture success is not style/business success. One task, one run per
arm and correlated platforms are descriptive evidence, not causal/statistical proof
of general quality or performance improvement. Publish equal/negative results too.
