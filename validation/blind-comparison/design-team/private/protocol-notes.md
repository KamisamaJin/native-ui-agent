# Blind evaluation protocol

The designer read only the three explicitly permitted files: Reply's Email.kt and EmailAttachment.kt, and AlertToast's Package.swift. No Skill, implementation, prior evaluation, or parent-conversation material was read. The SVG is an independently authored vector reference. There are no claimed execution results in these artifacts.

## Separation and sequence

1. Give both implementers only `public/brief.md` and `public/reference.svg`, the same task budget, and their assigned working environment. Do not disclose the fixture data, sampling plan, or assignment-to-Skill map to the designer/reviewer.
2. Freeze each first implementation as D0, recording an immutable revision/hash and the build toolchain. The read-only self-review happens after this freeze and before hidden initial feedback. Implementers may build/render public or self-chosen inputs and write `self_review.json`; they must not modify D0. A concrete observed defect with a public rule ID counts as detection; a generic possibility does not.
3. A separate harness operator runs the six `initial` fixtures on both platforms, with identical fixed configurations for both groups. Capture native outputs, build/runtime errors, semantics, actual interaction events when executable, and measurement metadata. Do not feed the oracle to either implementation process. Do not select attractive screenshots or adjust fixtures after seeing a group result.
4. Remove group, Skill, directory, author, commit, and tool-chain clues from the review package. Label screenshots and measured records with randomized anonymous implementation IDs, platform, fixture pseudonym, appearance, logical width, text setting, and direction. Randomize A/B placement independently across review pages. Do not disclose the Skill map to this reviewer during repair or reassessment.
5. Review the initial hidden cases. Return each team only its own factual failed public rule IDs, the exact observed symptom, evidence, and enough non-secret reproduction context to fix it. Never invent an interaction result from a screenshot or source inspection. Do not send the other team's output or the holdout data. Keep all true initial failures in the feedback; do not selectively suppress findings to shape the comparison.
6. Allow one repair round with the same fixed time budget for each team. Record D1 revision/hash. Re-run the six initial fixtures and the two previously undisclosed `repair_holdout` fixtures. Holdout expectations introduce no new requirement. Report initial-to-repair changes and holdout outcomes separately.

There are six fixed initial data configurations plus two fixed repair holdouts. Each configuration runs on Compose and SwiftUI, so the initial matrix is 12 platform renders before action/scroll samples, and repair adds four holdout platform renders. The per-platform font settings in the oracle are deliberate native categories rather than a claim that their glyph metrics are identical.

## What is evidence, and what is missing

The harness operator reports that the real Android probe exposes full unmerged semantics and executable native OnClick actions. The iOS UIHostingController unit-test probe compiles and renders, but its AX export is empty even with a known Button accessibility identifier. Native iOS PNG and Apple Vision OCR are available. This is a known harness evidence boundary, not a per-component accessibility failure. For this run, iOS A11Y declarations use explicit source review; runtime A11Y observations remain `not_assessed`, and iOS callback/tap behavior without actual UI events remains `not_executed`. The reviewer has not independently executed that probe and must attribute this capability report to the harness operator.

- A compiler/build failure or a component that cannot mount is a **blocking defect**, separate from visual/function scores. Preserve native logs, tool versions, and the attempted fixture. Subsequent rule outcomes are `blocked`, not `passed` or automatic zero-defect outcomes. A capture failure attributable only to the harness is `infrastructure_error`; retry the same fixture after correcting the harness without changing component source, and preserve both attempts.
- A native semantics assertion can pass only with captured native semantics or actual instrumented callback events. A source declaration of an onClick is not proof that a tap reaches the callback. A screenshot of a Retry button is not proof that it sends the correct ID. If interaction automation cannot run, mark those checks `not_executed`; source review may flag a known defect but cannot replace executed interaction success.
- Android Compose test semantics may expose fractions and full text. SwiftUI native accessibility may expose percentage strings instead of a numerical fraction. Record the available representation. Check fractions through native semantics when available and check the published percentage otherwise; use source review only to support the unavailable fraction check, with its method stated. Do not promote absent native evidence to a native-semantic pass.
- Identifiers are public requirements. If one is absent, record TQ-A11Y-01 as a failure. Attempt alternate native text/role inspection to avoid losing unrelated evidence, while marking checks that still cannot be evaluated `unscorable`.
- An identifier existing in source or an offscreen view is not proof that it is visible. Baseline semantics snapshots should include visibility/viewport information. Hidden collapsed rows must be absent from the tree, whereas expanded rows beyond a viewport may exist offscreen and be inspectable after native scrolling.
- Save capture density, logical viewport bounds, actual text category/font scale, locale/layout direction, color scheme, safe-area/inset policy, and scroll offset. Native PNGs must come from the component running in its real host. Do not use a browser rendering or a reconstructed screenshot as implementation evidence.

## Sampling and evaluation

The fixture matrix and deterministic derivation/checker are in `oracle.json`. They describe expected values, never observed outcomes. Baseline captures include the full panel when it fits. When it is taller than the fixed viewport, save a top viewport, scroll the common parent, and save the bottom viewport with an overlapping row. Use those to assess the whole panel. Keep the viewport dimensions fixed; do not shrink text or widen the host to make it fit. The component is not required to fit every row inside one screenshot.

Use the same host background, outer 16-unit margins, safe-area handling, and parent scroll container for both implementations on a platform. The `panel_width` in the oracle is the width offered to the component after those host margins, not the device's full width. Pixel coordinates must be converted to logical units using recorded native density. Sample flat fills away from anti-aliased boundaries and text, with a 3 × 3 interior median where possible. Geometry tolerance is ±2 logical units at default text size; RGB tolerance is ±12 per channel; normalized progress tolerance is 0.002. Treat 0% and 100% fill endpoints as particular boundary checks. Color and geometry checks are separate from typography/glyph quality.

Native semantics normally check exact summary/count/status copy, ordering, hidden rows, retry visibility, full names, progress, state labels, and callbacks. Native pixels normally check border/padding/corner/track/control sizes, palette, clipping, flow direction, and relative alignment. Build plus source review check the public API, deployment compatibility, nominal font values, and controlled state. These methods are listed per rule; a method list is not a claim that the method was executed.

Some expectations are not reliably reducible to a numerical score:

- System-font weight, multiline ellipsis, bidi ordering, and assistive-technology announcements vary by OS version and native accessibility bridge. Use native artifacts and source evidence; leave screen-reader speaking order `not_executed` without a real accessibility traversal.
- Pixel inference of progress direction is unreliable at 0%/100%; use a fractional running/aggregate value and the bar's native bounds. A rounded cap near 0% can change apparent width slightly. Do not claim RTL success from the root direction flag alone.
- Font scaling cannot be proven by one large screenshot alone. Compare the default baseline and large native typography evidence, or inspect an actually executed scale change; inspect nominal scaling implementation when necessary. Compare intent and legibility across platforms, not glyph-by-glyph identity.
- Visual hierarchy, intentional alignment, natural row rhythm, density, and the reference's level of polish require blinded AI visual judgment (TQ-VIS-01). Review legibility, clipping, and long-text behavior in every available viewport as TQ-VIS-02, supported by measurable overlaps where possible. Use a 1–5 anchored score (1 unusable/unstructured; 2 major visible flaws; 3 usable with conspicuous inconsistencies; 4 coherent with small flaws; 5 coherent, clear, and polished), plus rule-specific observations. Do not substitute a preferred unrelated visual style for the public reference. This is an independent AI review, not a human expert evaluation.
- Actual touch target area must come from native hit bounds or real coordinate-hit testing. A visible 48-high outline is useful pixel evidence but is not alone proof of hit behavior. Source review can supplement, not manufacture executed success.

Report each rule/case with `passed`, `failed`, `not_executed`, `not_assessed`, `unscorable`, `blocked`, or `infrastructure_error`, the actual method, and an evidence path. Use `not_assessed` when there is no sufficient native artifact, including lower rows outside a fixed viewport with no scroll capture; this is neither pass nor fail and must not be mislabeled component clipping. Use `unscorable` when an artifact exists but cannot establish a valid measurement. A passing-looking screenshot cannot discharge an unavailable behavior check. Keep visual rating, rule conformance, build/render blockers, and evidence coverage as separate columns. Never summarize missing evidence as “all tests passed.” The independent visual reviewer in this experiment is an AI reviewer, not a human expert.

## Reviewer blindness

The designer/reviewer can later receive anonymous screenshots, native measurement records, and specific source excerpts with group/Skill clues removed when source review is required. The reviewer must not read implementation directories or Skill files, recover authorship clues, or learn group assignments. Source excerpts should be the smallest portions needed to adjudicate a public rule. The independent harness operator holds the assignment key and exact private fixture inputs. A public failure report may quote the tested output and public rule without publishing the remaining hidden inputs.
